# 用现有数据检查编辑会不会改错

StyleBench-ZH 适合诊断重复表达、场景匹配和改写保真；DeliveryBench-ZH 适合判断成稿旁白与必要的计划、进展、操作说明。两者提供的是**合成任务上的模型输出、受控变体和模型标注**。它们可以帮助发现具体失败，尚不是经过人类确认的通用写作质量标准。

## 先读一个完整源家族

网站源码中的 `datasets.html` 现在按家族配对浏览，可按套件、阶段、文体、篇幅和标注状态筛选，并用直接链接定位家族。展开后按需读取 Hugging Face 固定 `v0.1.1` 的完整记录；网络不可用时可在页面载入已下载的 `samples.jsonl`，文件不上传。本地预览沿用 `python scripts/build_site.py --output ../site-preview --base-path / --commit unpublished`，再运行 `python -m http.server --directory ../site-preview 8765` 并访问 `http://localhost:8765/datasets.html`。正式版本站点仍按既有 Release 部署，不因本次浏览改动重新标记旧版本。

现有数据已经可以从 [StyleBench-ZH](https://huggingface.co/datasets/RedinGhost/StyleBench-ZH)、[DeliveryBench-ZH](https://huggingface.co/datasets/RedinGhost/DeliveryBench-ZH) 或 [v0.1.1 发布页](https://github.com/rrrrrredy/editorial-guard/releases/tag/v0.1.1) 下载。无需安装模型服务。下面的标准库示例支持仓库预览 JSON 和发布包的 `samples.jsonl`：

```sh
# 在本仓库根目录：统计公开预览，或查看原稿和变体。
python -X utf8 examples/read_dataset.py
python -X utf8 examples/read_dataset.py --suite DeliveryBench-ZH --family cal-0001

# 解压现有数据 ZIP 后：读取完整事实底稿、约束、两份标注及分歧。
python -X utf8 examples/read_dataset.py --input ../DeliveryBench-ZH/samples.jsonl --family cal-0001
python -X utf8 examples/read_dataset.py --input ../StyleBench-ZH/samples.jsonl
```

把路径替换成实际解压位置。仓库的 `datasets/public_samples.json` 是阅读预览，**不含完整事实底稿和标注**；发布包包含这些字段。示例只读取原记录，不给争议样本补标签、不生成改稿。完整家族输出是研究者阅读视图，包含答案侧材料，不能原样作为 solver 输入；正式评测沿用已有 solver/task-view 导出。

### 应该如何利用三个现有案例

| 家族 | 阅读重点 | 能回答的问题 |
| --- | --- | --- |
| StyleBench-ZH `cal-0000` | 原稿说明复检条件、效果未知及下一步核对计划；原稿的两份模型标注认为无需编辑。controlled 增加旁白，仍要逐句结合阶段判断。 | 编辑器会不会把有用的条件和不确定性当成冗余？模型认为无需修改的稿件会不会被无谓重写？ |
| DeliveryBench-ZH `cal-0001` | 任务明确要求计划。Codex 把来源及保真争议写进 process 标签；GLM 未判过程问题。完整记录保留双方理由。 | 过程语言检测是否混入了事实判断？同一句话在计划阶段与最终稿中的作用是否被正确理解？ |
| StyleBench-ZH `main-0439` | 原文只说 11 天运输记录不能推算全年；已有候选扩大成全年数据没有依据。 | 改写是否扩大否定范围，或添加原文没有的流程要求？见[保真失败及相反裁判意见](../reports/results.md#一次变得更清楚却扩大事实范围的改写)。 |

这些是实际已发布的合成任务及已保存的模型判断，不是人工真值。要比较改写方法，应固定同一事实底稿、阶段和来源家族，保留原稿、所有首次候选、必要信息与新增断言。不要用规则命中减少代替语义判断，也不要只挑指定字段一致的样本后声称覆盖了所有难例。

## 实际覆盖：行数之外还能看到什么

2026-10-27 从 v0.1.1 两个完整发布包复算；没有重新生成或标注样本。以下长度为 Python `len(input_text)`，包括 Markdown、空格和标点，不是纯汉字数。

| 公开内容 | StyleBench-ZH | DeliveryBench-ZH |
| --- | ---: | ---: |
| 源家族 / 实例 | 241 / 482 | 241 / 482 |
| 不同文本 | 439 | 440 |
| 家族内原稿与变体文本完全相同 | 43 对 | 42 对 |
| 正常模型输出字符数：最小 / 中位 / 最大 | 145 / 576 / 1,495 | 140 / 571 / 1,853 |
| 正常模型输出至少 1,000 字符 | 66 | 67 |
| 原稿阶段：plan / progress / final | 72 / 32 / 137 | 72 / 32 / 137 |
| 指定标签一致 / 争议 / 证据不足 | 131 / 339 / 12 | 133 / 341 / 8 |

相同文本对保留了原来“没有实际改动”的状态，不应机械删除；用于误改诊断时仍须确认任务和标签，**相同不等于质量合格**。它们不增加内容覆盖。detect、generate、workflow 视图增加的是任务接口，不增加源家族数。

完整包的前 3 条基础事实，去除虚构项目名和数值后，每套均为 7 类。它们与文体一一对应：行业分析—设备复检，技术解释—预算与采购，项目文档—软件用例与接口，工作报告—问卷与代表性，教程—预约与名额，邮件沟通—运输与签收，社交媒体短文—用电与负荷。长稿还带有补充事实，但这个底稿结构没有改变。**当前不能从“七种文体”推出独立覆盖了七种真实写作活动，也不能分离文体与事实类型的影响。** 示例输出保留规范化后的三条事实，便于复核该归类。

实际发布的三家生成供应商均覆盖短、中、长请求，分布并不均衡；示例按发布记录输出供应商 × 请求篇幅交叉表。不要把生成函数的默认供应商安排当作实际发布分布。长稿请求为 900—1,300 字，本版没有数千字文章、多篇同作者作品或真实用户修订历史的覆盖证据。

两套数据共 964 条实例，不等于 964 次独立效果实验。历史基础方法比较只有两个已暴露源家族，四状态干预来自同一源家族；重复运行、裁判票数和调用账本另计。[原始结果](../reports/results.md)没有证明 B4 比简短改写稳定更好。

## 下一批内容最值得回答的问题

先使用项目已有且有权使用的完整稿件，把它们作为开发案例，保留其模型生成或合成身份。这样的案例能说明具体改法和损伤，不能自动增加独立未见效果证据。

真正要补的是：在未参与规则形成的完整文章上，编辑是否减少重复论证、让关系更清楚，同时保留事实、条件、术语和作者语气。需要有权使用的数千字文章、同作者可比作品、作者修改意图和读者判断；不同事实内容应跨文体安排。比较简短提示与当前 Skill 的首次输出，允许原样保留，记录错误新增、信息删除、作者接受或撤销的修改及实际返工时间。先做少量有代表性的文章，看到具体收益或损伤后再决定是否扩充。当前没有这些材料与反馈，不能用更多同模板行数填补。
